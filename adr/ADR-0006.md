## Context

ADR-0003 decided that governance runs as code and leaves evidence. The contracts follow the Open Data Contract Standard, and [datacontract-cli](https://github.com/datacontract/datacontract-cli) already tests data against such a contract. The question a reviewer asks is why this repository has its own generator.

## One check, end to end

"No source identifier in Gold", on `gold/channel_quality`.

**1. Regulation row**, `governance/requirements.csv`

```
framework   GDPR-Art9
clause      Processing of data concerning health is prohibited without safeguards
control     no source identifier in any Gold dataset
check_kind  no_direct_identifier
dataset     gold/*
params      {"forbidden_columns": ["subject_src"]}
severity    block
```

**2. Contract rule**, `contracts/gold_channel_quality.yaml`, the same rule stated by the contract

```yaml
quality:
  - type: custom
    engine: ecog-lakehouse
    implementation:
      check_kind: no_direct_identifier
      params: {"forbidden_columns": ["subject_src"]}
```

**3. Generated SQL**, published in `docs/data/checks.json`, rerun in the browser

```sql
SELECT count(*) AS observed
FROM information_schema.columns
WHERE table_name = 'gold_channel_quality' AND column_name IN ('subject_src')
```

**4. Evidence row**, `gold/evidence`

```
check_id         GDPR-Art9/no_direct_identifier/gold/channel_quality/['subject_src']
clause           Processing of data concerning health is prohibited without safeguards
result           pass        observed 0   expected 0
dataset_version  d933dd02…eb597d
engine_version   1.5.5
git_commit       15c59b67
ran_at           2026-09-24 23:09:53
```

## Options considered

```
                     contract rules   evidence   regulation rows   same SQL in the browser
datacontract-cli           ✔             ✔             ✘                    ✘
this generator             ✔             ✔             ✔                    ✔
```

| Option | Summary | Rejected because |
|---|---|---|
| datacontract-cli | Tests a contract against the data and reports the results | Its input is the contract, so a row of `requirements.csv` has no way in; it is a Python command line tool, so the page cannot rerun its checks |
| datacontract-cli for the contracts, a generator for the requirements | Each tool on its own input | Two engines and two evidence formats for one kind of check |
| One generator for both inputs | Nine SQL templates in `sql/checks/`, a 10 line placeholder renderer, `pipeline/checks.py` | chosen |

## Decision

One generator reads both `governance/requirements.csv` and the contracts, and renders every rule as plain SQL from a template. The SQL text is the check: the pipeline runs it, `make publish` writes it to `docs/data/checks.json`, and the page runs the same text in DuckDB-WASM. The clause of a requirement row is copied into its evidence row, so each result names the regulation it answers.

## Consequences

Positive:

- One evidence format for regulation and contract rules. (observed: [tests/test_checks.py](../tests/test_checks.py), `test_evidence_records_why_each_check_exists`)
- The browser and the pipeline cannot disagree on what a check is. (observed: [tests/test_gold.py](../tests/test_gold.py), `test_published_checks_rerun_over_the_published_files_alone`)
- No dependency beyond PyYAML. (observed: `dependencies` in [pyproject.toml](../pyproject.toml))
- Fault G, which is planted in a generator, has a generator to live in. (observed: [tests/test_faults.py](../tests/test_faults.py), `test_fault_g_plant_is_refused_by_the_generator_and_the_fix_is_not`)

Negative:

- Eight check kinds, not the range of a maintained tool.
- A new kind is a template and a branch in `pipeline/checks.py`.

The contracts stay standard, their custom rules sit in the standard's own `engine` slot, so datacontract-cli can still read them.
