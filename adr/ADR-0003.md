# ADR-0003: Governance as code, with validation evidence as a build artefact

## Context

ISO 13485 and 21 CFR Part 11 require validated systems and documented change control. Document-based validation ages the day it is written and every change reopens it. The FDA's computer software assurance guidance accepts risk-based, automated evidence.

## Options considered

| Option | Summary | Rejected because |
|---|---|---|
| Governance in documents and periodic audits | Standard practice in regulated companies | Evidence ages the day it is written; every change re-opens the validation question |
| Data contracts, checks and lineage versioned in the repository, run on every change, evidence records stored with the run | Validation state is always current and reproducible | chosen |

## Decision

Every dataset has a typed data contract (Open Data Contract Standard). Every contract has checks. Regulatory requirements are rows in a metadata table that generates checks, so adding a framework is adding rows. Every run writes an evidence record: what was checked, against which dataset version, with which result, by which job.

## Consequences

Positive:

- Computer software assurance is served by the pipeline itself. (observed: [tests/test_evidence.py](../tests/test_evidence.py), `test_evidence_is_append_only_and_versions_repeat_for_identical_inputs`)
- Audit questions become queries. (observed: [docs/manual.md](../docs/manual.md) section 4.2)

Negative:

- Contracts have to be maintained by domain owners, which is a habit to build.
- A check that is wrong fails loudly and blocks a release. That is the point, but it costs time early on.
